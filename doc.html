Abstract

This report presents the analysis of the FOOD SEWA project based on the actual PHP codebase found in the repository. The application was previously branded as Foodmandu and is now documented as FOOD SEWA across its public and admin interfaces. The system is a web-based food ordering and delivery platform built with plain PHP, MySQL, Bootstrap, Leaflet, and third-party payment APIs.

The application supports customer registration and login, category-based food browsing, guest and authenticated carts, wishlist management, address saving through text input or map pinning, checkout with coupon support, and payment processing through Stripe, eSewa, and Khalti. The admin panel provides category and food management, user status control, payment log review, delivery status management, coupon administration, and runtime restaurant-coordinate configuration.

The most significant technical contribution of the project lies in its applied algorithms: file-based rate limiting, session timeout enforcement, guest-state merge after login, coupon eligibility checks, unique order and tracking code generation, transactional payment verification with stock deduction, validated delivery-state transitions, route caching with OSRM fallback, Haversine distance estimation, interpolation of rider position along a route, and delayed-delivery coupon claiming. The platform also separates public and owner tracking views to protect customer location privacy.

Keywords: Food delivery, PHP, MySQL, Stripe, eSewa, Khalti, OSRM, Haversine distance, live tracking, coupon logic, session security.

Chapter 1: Introduction

1.1 Introduction

FOOD SEWA is a web-based food delivery system that was previously known as Foodmandu. The repository contains a full-stack PHP application with separate user and admin interfaces, a MySQL database dump, shared business-logic helpers, and payment/tracking integrations. The application is designed for customers who browse foods, manage carts and wishlists, save delivery addresses, make online payments, and monitor order progress after checkout.

Unlike a static academic prototype, the codebase implements concrete operational logic: guest-state persistence through cookies, order creation inside database transactions, payment verification against gateway responses, stock deduction only after verified payment, dynamic delivery-state progression, and route-based tracking payloads derived from restaurant and customer coordinates. This report therefore focuses on the implemented behavior observed in the repository rather than on generic food-delivery assumptions.

The system supports two authenticated roles in code: admin and user. It also supports a public tracking viewer who can inspect delivery status using a tracking number but cannot access route-sensitive owner details. This limited but deliberate role model is more accurate than the broader multi-actor claims found in some generic report templates.

1.2 Problem Statement

Traditional food ordering is slow, difficult to audit, and inconvenient for both customers and operators. Phone-based ordering lacks structured menus, real-time availability checks, verified payment handling, and consistent delivery status updates. At the same time, many academic demo systems describe features such as live tracking or compensation logic without implementing the required algorithms in code.

The repository addresses these problems by combining menu management, checkout validation, coupon logic, gateway-based payment verification, delivery-state control, and simulated live route tracking in a single PHP application. The delayed-delivery coupon flow is especially important because it is not a visual-only feature: it relies on elapsed-time checks, ownership validation, duplicate-prevention logic, and coupon generation with unique codes.

1.3 Objectives

  1. To build a functioning PHP/MySQL food ordering platform with user and admin panels.
  2. To manage categories, foods, stock quantity, user status, coupons, payments, and delivery status from an admin dashboard.
  3. To provide customer-side flows for registration, login, address management, cart handling, wishlist handling, checkout, payment, and order history.
  4. To integrate Stripe, eSewa, and Khalti payment gateways with verification logic rather than simple redirection.
  5. To implement route-aware delivery tracking, privacy-aware public tracking output, and delayed-delivery coupon claims.
  6. To document the real algorithms used in the repository and map them to their source files.

1.4 Scope and Limitations

Scope: the codebase includes a public storefront, user authentication and account management, address capture using text or map coordinates, order placement, multi-gateway payment initiation and verification, live tracking simulation, coupon management, user support tickets, and admin-side management of orders, users, payments, foods, categories, coupons, and restaurant coordinates.

Limitations: the repository does not implement a separate restaurant-owner role, a delivery-rider login role, ratings/reviews, advanced search/sorting, webhook-based asynchronous payment updates, or real rider GPS capture. Tracking is calculated from route progress and time, not from a real rider device. Support tickets are created at runtime if the table is missing, but there is no admin-side support ticket dashboard in the current code.

Chapter 2: Background Study and Literature Review

2.1 Background Study

A modern food-delivery platform typically requires more than a storefront. At minimum, it must support identity management, product visibility, cart persistence, order capture, payment confirmation, fulfillment tracking, and post-order support. This repository addresses those concerns using a classic server-rendered architecture. Pages are implemented with plain PHP, Bootstrap-based markup, and JavaScript polling where near-real-time updates are required.

The project also reflects a common local-development deployment style in Nepalese academic projects: Laragon for Apache and MySQL, phpMyAdmin-based data dumps, and payment integration against sandbox or test APIs. The repository demonstrates that even without a heavyweight framework, an application can still apply transactional integrity, route caching, secure password hashing, CSRF tokens, and delivery-state validation.

2.2 Repository-Specific Gap Analysis

Many academic reports describe broad features such as "real-time tracking", "multiple payment systems", or "delayed compensation" without linking them to concrete code. In this repository, those features are implemented and traceable. The following table summarizes the difference between generic expectations and the observed implementation.

3.2.3 Database Schema Summary

The schema follows a normalized transactional design. Snapshot tables such as order_items and payment raw responses preserve historical information even if prices or stock change later. Coupon ownership and redemption are modeled separately, allowing both global and private late coupons. The admin and user roles use separate tables rather than a shared discriminator column.

3.2.4 Interface Design

The UI uses server-rendered Bootstrap layouts. The public storefront offers category filtering, add-to-cart and wishlist actions, and checkout entry. Address and restaurant settings pages use Leaflet with OpenStreetMap tiles to capture coordinates. Order tracking uses polling rather than websockets and reveals more data to the order owner than to a public viewer. This dual-visibility design is part of the system's security model, not only its presentation layer.

3.2.5 Algorithms Used in the Project

Audit basis: the algorithm descriptions below were derived from the implemented logic in components/helpers.php, components/guards.php, components/functions.php, components/payment/*.php, track.php, and the related user/admin pages.

Algorithm 1: Session Timeout and Access Guard

Implemented in: components/guards.php

The application maintains both idle timeout and absolute timeout values. Every authenticated request updates the last-seen timestamp, unless either threshold has been exceeded, in which case the session is invalidated and the user is redirected to the correct login page.

Input: current session, started_at, last_seen, idle_limit, absolute_limit If started_at or last_seen is missing: initialize both timestamps and allow request Else if (now - last_seen) > idle_limit: expire session Else if (now - started_at) > absolute_limit: expire session Else: update last_seen and allow request

Algorithm 2: File-Based Rate Limiting

Implemented in: components/helpers.php

Rate limits are stored in JSON files under uploads/.ratelimit. Each bucket key is hashed as sha1(bucket|identifier), and the file is locked with flock before reading or writing. This creates a lightweight fixed-window counter without requiring Redis or database tables.

hash = sha1(bucket + "|" + identifier) Open uploads/.ratelimit/hash.json with create mode Lock file exclusively Read window_start and count If current window expired: reset window_start and count If count >= maxAttempts: deny request Else: increment count and allow Write JSON back to file Unlock and close

Algorithm 3: Guest Cart and Wishlist Merge

Implemented in: components/functions.php via merge_guest_state_into_user()

After login or registration, guest state associated with guest_session_id is merged into the authenticated user's cart and wishlist. Duplicate cart items are merged by summing quantities and capping them at MAX_CART_ITEM_QTY. Duplicate wishlist items are ignored. The guest cart and wishlist containers are removed after merge.

Read guest_session_id cookie If guest cart exists: For each guest cart item: If same food exists in user cart: newQty = min(existingQty + guestQty, MAX_CART_ITEM_QTY) update existing row Else: insert guest item into user cart delete guest cart If guest wishlist exists: For each guest wishlist item: If same food not already in user wishlist: insert it delete guest wishlist

Algorithm 4: Address Validation and Normalization

Implemented in: components/functions.php via save_user_address()

Address creation accepts either structured text fields (Address Line 1 + City + Zone) or a map pin (lat/lng). The algorithm validates address naming, coordinates, field length, and allowed characters. If the new address is marked as default, all previous addresses for the same user are first unset inside a transaction.

Normalize address_name into Home / Office / Other / custom text Validate custom name and address text fields Check lat/lng completeness and coordinate bounds Require either structured text address or map coordinates Start transaction If is_default: unset previous default addresses for user Insert normalized address row Commit transaction

Algorithm 5: Coupon Validation and Discount Calculation

Implemented in: find_coupon() and calculate_discount() in components/functions.php

Coupon validation checks format, existence, status, expiry, usage count, and user lock. Discount calculation then computes a percentage-based reduction and caps the discount at the subtotal to avoid negative totals.

Normalize coupon code to uppercase Reject invalid format Fetch coupon by code Reject if missing, inactive, expired, exhausted, or locked to another user percent = coupon.discount_percent discount = round(subtotal * percent / 100, 2) discount = min(discount, subtotal)

Algorithm 6: Unique Order and Tracking Code Generation

Implemented in: random_code(), generate_unique_order_code(), and generate_unique_tracking_number()

The system uses random_bytes() for randomness and retries up to 10 times to avoid collisions. Order codes use the prefix ORD, while tracking numbers use TRK. Each candidate is checked against the database before acceptance.

Repeat up to 10 times: candidate = prefix + UPPERCASE(bin2hex(random_bytes(n))) If candidate not found in corresponding table: return candidate If no unique candidate found: throw error

Algorithm 7: Order Creation from Cart

Implemented in: create_order_from_cart()

Order creation validates ownership of the selected address, reads cart items, checks item availability and stock, optionally validates a coupon, computes the discount, and stores the order plus snapshot order-items inside a database transaction. Stock is not deducted at this stage because payment may fail.

Assert address belongs to user Fetch cart items Reject empty cart For each item: reject inactive food reject if qty > current stock accumulate subtotal If coupon code provided: validate coupon if private late coupon and subtotal below min order: reject Compute discount and total Start transaction Generate unique order code Insert order row Insert snapshot order_items rows Commit

Algorithm 8: Payment Verification and Stock Deduction

Implemented in: user/payment_success.php and process_payment_success()

Payment handling is intentionally two-step: the success page verifies gateway responses, then the core function locks the order, prevents reuse of the same transaction reference for another order, records successful payment if needed, verifies stock under lock, deducts stock, updates order payment status, registers coupon usage, and clears the user's cart.

Verify gateway response and amount Start transaction Lock order row FOR UPDATE Reject if amount mismatches order total Lock existing SUCCESS payment row for same gateway+txn_ref If same txn_ref belongs to another order: reject If payment not already recorded: insert SUCCESS payment If order already PAID: return safely Lock ordered food rows FOR UPDATE If any stock is insufficient: mark order as PAID + CANCELLED + refund_required commit and return refund_required For each item: decrement stock only if enough stock remains Generate tracking number if missing Mark order PAID Register coupon usage if coupon exists Clear user's cart Commit

Algorithm 9: Delivery Status Transition Validation

Implemented in: update_delivery_status()

Delivery states are not freely editable. The algorithm enforces allowed transitions and prevents delivery actions on unpaid orders. It also stamps delivery_start_at when delivery begins and delivered_at when the order reaches the delivered state.

Allowed transitions: PENDING -> CONFIRMED or CANCELLED CONFIRMED -> OUT_FOR_DELIVERY or CANCELLED OUT_FOR_DELIVERY -> DELIVERED or CANCELLED DELIVERED -> no transition CANCELLED -> no transition Reject transition if not in allowed set Reject OUT_FOR_DELIVERY or DELIVERED if payment_status != PAID If moving to OUT_FOR_DELIVERY: set delivery_start_at if null If moving to DELIVERED: set delivered_at = NOW()

Algorithm 10: Late Coupon Claim Logic

Implemented in: late_coupon_claimable_for_order(), generate_private_late_coupon(), and claim_late_coupon_for_order()

Late coupons are claim-based, not background-generated. The owner must explicitly request them from the tracking endpoint after the configured claim window has elapsed. The system locks the order row, prevents duplicate generation, and issues a user-specific coupon with one allowed use and a seven-day expiry.

Lock order row FOR UPDATE Reject if order not found or wrong user If coupon already generated: return latest private coupon Reject unless delivery_status == OUT_FOR_DELIVERY Reject if delivered_at exists or delivery_start_at missing elapsed = now - delivery_start_at If elapsed <= claim_limit: return null Generate unique LATE-prefixed coupon Mark order.late_coupon_generated = 1 Commit and return coupon

Algorithm 11: Haversine Distance Fallback

Implemented in: haversine_distance_m() and fallback_route_data()

If routing data is unavailable, the system computes a straight-line distance using the Haversine formula, then estimates duration with a fixed average speed of 8.33 meters per second. This guarantees tracking output even when external routing is unavailable.

dLat = radians(lat2 - lat1) dLng = radians(lng2 - lng1) a = sin(dLat/2)^2 + cos(lat1) * cos(lat2) * sin(dLng/2)^2 c = 2 * atan2(sqrt(a), sqrt(1-a)) distance = earthRadius * c duration = max(60, ceil(distance / 8.33))

Algorithm 12: Route Retrieval with Memory and File Cache

Implemented in: route_data()

The route service first checks an in-memory static cache, then a hashed JSON file under uploads/.route_cache_*.json, then calls the OSRM public routing API. If the API fails or returns invalid geometry, the fallback algorithm is used instead. Successful results are written back to the file cache with a six-hour freshness limit.

cacheKey = rounded coordinates If route exists in static cache: return it If route cache file exists and age <= 21600 seconds: decode and return it If cURL unavailable: use fallback route and cache it Call OSRM API If HTTP error or invalid geometry: use fallback route and cache it Else: normalize geometry into [lat,lng] path store duration, distance, path, source=osrm cache and return

Algorithm 13: Rider Position Interpolation Along a Route

Implemented in: point_on_path_by_progress() and tracking_payload()

The system computes progress as elapsed delivery time divided by route duration. It then walks the polyline segment by segment, measuring segment distances with Haversine, until the target travel distance is reached. The rider point is then linearly interpolated inside that segment. This produces a continuously moving rider marker even though the app does not ingest live GPS packets.

If progress <= 0: return first path point If progress >= 1: return last path point Measure every segment distance on the path totalDistance = sum(segmentDistances) targetDistance = totalDistance * progress Walk segments until cumulativeDistance reaches targetDistance ratio = (targetDistance - walkedBeforeSegment) / currentSegmentDistance Return interpolated point between segment start and end

Algorithm 14: Public vs Owner Tracking Response Shaping

Implemented in: track.php and user/track_order_realtime.php

The public tracking endpoint supports any valid tracking number but strips sensitive route and coupon metadata when the viewer is not the owner of the order. Owners receive route path, rider coordinates, coupon claimability, and order code; public viewers only receive safe status data. This is a small but important privacy algorithm built into the response layer.

Fetch order by tracking number Build full tracking payload If viewer is owner: include route_path, restaurant, customer, rider, coupon fields, order_code Else: remove route_path, restaurant, customer, rider, coupon_due_at, late_coupon_claimed, late_coupon_claimable, late_coupon_claim_minutes, late_coupon_min_order_amount Return remaining payload as JSON
Admin marks OUT_FOR_DELIVERY

4.1.3 Security and Validation Controls

The project applies practical server-side safeguards throughout the codebase. Password strength validation enforces uppercase, lowercase, number, special character, and minimum-length rules. Uploaded food images are verified by MIME type, extension, and maximum size before being saved. Coupon codes, tracking numbers, coordinates, names, phone numbers, and order codes all pass through explicit validator functions before use.

The system also avoids several common mistakes in simpler student projects. Sensitive payment results are not trusted blindly from the query string; instead, they are reverified by API calls or session-bound identifiers. Delivery cannot begin until payment is marked as paid. Public tracking does not expose customer route geometry. Session fixation risk is reduced through session_regenerate_id(true) after authentication and timeout recovery.

4.1.4 Payment and Tracking Integration

Payment flow is split between redirection and verification. Stripe uses checkout sessions, eSewa builds a signed request payload with HMAC-SHA256, and Khalti creates an initiated payment session whose status is later looked up. All three gateways converge into the same transactional payment-success function, ensuring that order state changes are centralized.

Tracking flow is likewise centralized. Admins manage delivery states, while the tracking layer derives progress from timestamps and route data. Public and owner views consume the same core payload but receive different field subsets depending on ownership. This keeps tracking behavior consistent while maintaining privacy boundaries.

Chapter 5: Conclusion and Future Recommendations

5.1 Outcomes

The repository delivers a working food-ordering workflow with meaningful backend logic rather than only a visual prototype. The most important outcomes are the transactional order/payment path, role-separated admin and user views, secure authentication controls, verified payment gateway integration, and route-aware delivery tracking. The code also demonstrates that a plain-PHP application can still structure its logic around reusable functions and consistent validation rules.

From an academic-report perspective, the biggest outcome of this analysis is that the system's algorithms are identifiable and documentable. The project does not merely mention delayed compensation, route tracking, or payment verification; it actually implements them with concrete conditions, locks, cache layers, and state transitions.

5.2 Conclusion

FOOD SEWA, previously branded as Foodmandu, is a credible student project because it connects user-facing flows to real backend rules. The repository demonstrates good control over session handling, data validation, cart persistence, payment state management, and delivery-state logic. Its strongest technical areas are the shared business-logic layer in components/functions.php and the way multiple payment gateways are normalized into a single payment-success transaction.

At the same time, the project remains intentionally lightweight. It is server-rendered, easy to deploy on a local Laragon setup, and understandable without a framework. That simplicity is a strength in an academic setting because the algorithms and data flow are visible rather than hidden behind framework abstractions.

5.3 Future Recommendations

  1. Introduce webhook-based asynchronous payment confirmation so that the system does not depend only on browser return URLs.
  2. Add a dedicated rider or delivery-agent role with true GPS updates instead of time-based interpolation.
  3. Create migrations for runtime-created tables such as support_tickets to remove schema drift.
  4. Add search, sorting, and richer order filtering in both the user and admin interfaces.
  5. Implement automated tests for validators, coupon flows, payment success transitions, and tracking payload privacy rules.
  6. Add notification integrations (email/SMS/push) for payment result, dispatch, and delivery completion.
  7. Normalize the project branding so the academic report title and UI brand no longer diverge.
